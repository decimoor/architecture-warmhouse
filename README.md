### 1. Описание функциональности монолитного приложения

**Управление датчиками:**

- Приложение позволяет создавать, просматривать, изменять и удалять датчики через REST API.
- Для датчика хранятся название, тип, местоположение, единица измерения, текущее значение, статус и время последнего обновления.
- Отдельный метод API позволяет обновить значение и статус датчика.

**Мониторинг температуры:**

- Приложение получает текущую температуру из внешнего `temperature-api` по идентификатору датчика или названию местоположения.
- При запросе списка датчиков или одного температурного датчика приложение подставляет актуальные значение, статус и время обновления из `temperature-api` в возвращаемые данные.
- Клиент может запросить температуру по местоположению и получить значение, единицу измерения, статус, время измерения и описание.

В предоставленном коде нет веб-интерфейса, непосредственного подключения физических датчиков и API управления отоплением. Взаимодействие с приложением реализовано через HTTP API.

### 2. Анализ архитектуры монолитного приложения

- **Язык и библиотеки:** Go, веб-фреймворк Gin, драйвер PostgreSQL `pgx/v5`.
- **База данных:** PostgreSQL. База `smarthome` содержит таблицу `sensors`, в которой хранятся сведения о датчиках и их последние сохраненные значения.
- **Структура:** HTTP-обработчики, модели, сервис получения температуры и доступ к данным разнесены по пакетам, но выполняются в одном процессе и развертываются как одно приложение.
- **Взаимодействие:** клиенты используют синхронный REST API. Приложение синхронно обращается к PostgreSQL и по HTTP к `temperature-api`; брокер сообщений и асинхронная обработка не используются.
- **Обработка запросов:** при получении списка датчиков приложение последовательно запрашивает актуальную температуру для каждого температурного датчика. Если запрос к внешнему API завершился ошибкой, приложение возвращает последние сохраненные данные датчика.
- **Масштабирование:** масштабировать можно только все приложение целиком, а не отдельно операции с реестром датчиков и получение данных из `temperature-api`.
- **Развёртывание:** приложение запускается в одном контейнере. Обновление требует перезапуска всего приложения; корректное завершение HTTP-сервера снижает риск обрыва запросов, но не устраняет простой при обновлении.
- **Сильные стороны:** небольшой объем кода, простой локальный запуск и развертывание, прямые вызовы между компонентами и единая база данных.

### 3. Определение доменов и границы контекстов

По фактически реализованной функциональности выделяются два домена:

1. **Управление датчиками** — создание, изменение, удаление и просмотр реестра датчиков. К этому домену относятся идентификатор, название, тип, местоположение и единица измерения датчика. Основная модель — `Sensor`, данные хранятся в таблице `sensors`.
2. **Мониторинг температуры** — получение текущих показаний из `temperature-api`, обновление значения и статуса датчика и предоставление этих данных клиенту. Используются значение температуры, статус и время обновления.

Эти домены не изолированы друг от друга: они используют общие модель `Sensor`, таблицу `sensors` и обработчик `SensorHandler`. Отдельные домены управления отоплением, домами, пользователями и правами доступа в существующем приложении не реализованы.

### 4. Проблемы монолитного решения

- **Связанность функций:** управление реестром датчиков и мониторинг температуры используют общие модель, обработчик и базу данных, поэтому изменения могут затрагивать обе функции.
- **Общее масштабирование:** нельзя независимо масштабировать операции с реестром датчиков и запросы к внешнему API температуры.
- **Синхронная зависимость:** недоступность или замедление `temperature-api` увеличивает время ответа клиенту; при получении списка внешние запросы выполняются последовательно для каждого температурного датчика.
- **Общая точка отказа:** сбой приложения или базы данных одновременно затрагивает управление датчиками и мониторинг температуры.
- **Простой при развертывании:** любое обновление требует перезапуска всего приложения.
- **Общий релизный цикл:** изменения любой функции требуют проверки и выпуска всего приложения.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1. сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2. Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3. Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
